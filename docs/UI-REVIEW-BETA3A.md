# Beta 3a 界面检查记录

## 上一版为什么显得松散、杂乱

1. **没有建立页面的内容宽度规则。** 设置页把 `widthIn` 放在已经由 `weight` 确定宽度的链路里，父布局的最小宽度覆盖了预期上限。首页和聊天也直接跟随可用宽度伸展。大窗口中标题、文件名、人物和表单控制端点被拉得很远。
2. **组件边界混用。** `desktopClick` 默认裁切所有可点击对象，玻璃主题使用百分比 50 的胶囊形状。主题卡片也继承这个形状，文字和缩略图被裁去。缩略图使用物理像素，Retina 下比例不一致。
3. **缺少稀疏内容的设计。** 任务页只顺序堆放标题和文字，没有分区、数量和明确空状态。预览数据很少，却未专门检查这种情况。
4. **把材质效果加在错误层级。** 给整个导航轨和主面板套浮动边框、阴影，产生贯穿窗口的大圆角外壳，与内部表单和小控件不一致。
5. **摘要没有应用展示清理。** 移动端内部上下文标记、附件服务器路径直接显示在首页与历史列表中。

上一轮验收主要覆盖 1440×900、有内容的演示页面，遗漏了用户截图中的 2048 宽窗口、侧栏收起、稀疏任务与主题点击后的 Retina 状态。这些是布局实现和视觉检查的问题。

## 本次处理原则

- 在释放父容器最小宽度约束后限制内容宽度：首页、历史、任务最多 1360 dp，设置连同子导航最多 1160 dp，聊天最多 1100 dp。更窄窗口随可用宽度缩小。
- 用分区和对齐组织内容。首页四个区域共享两列网格；任务按状态分列；设置将主题与资料分开。
- 卡片、控件、导航分别定义轮廓。卡片裁切显式使用自己的形状；主题缩略图用归一化坐标，不再依赖物理像素尺寸。
- 保留哑光、纸张和半透明层次的差异，避免全窗口多层浮动框。
- 摘要仅清理展示字符串，不修改原始消息、服务器文件路径或消息提交协议。

截图和自动检查是对具体布局状态的验证，不能代替用户在 Mac 上的使用感受。
