# Hermes Desktop 2.0.0 Mac 打包修復

日期：2026-10-08；打包修訂：r2；應用版本仍為 2.0.0。

## 現象與定位

使用者截圖中，Finder 開啟的名稱是 `Hermes-macOS-arm64-2.0.0`，圖示為通用應用加停用標識，提示“可能已損壞或不完整”。

原交付檔案實際為 `Hermes-macOS-arm64-2.0.0.app.zip`，並非 DMG。ZIP 頂層有兩項：`Hermes.app/` 和 `验收说明.md`。Archive Utility 在為多個頂層專案建立外層目錄時，可能沿用去掉 `.zip` 後的名稱，使外層也成為 `.app`。外層缺少 `Contents/Info.plist` 和啟動入口，符合截圖所見現象。尚未取得受影響 Mac 的解壓目錄或啟動日誌，因此這是有包結構與截圖支援的診斷，不能據此排除其他原生啟動問題。

## 修復

- 修訂安裝包頂層只有 `Hermes.app/`，並顯式寫入目錄條目。
- 應用內所有 534 個原始檔案條目保持位元組和 Unix 模式一致，保留原簽名；刪除的是包外說明檔案。
- 構建指令碼統一使用 `packaging/macos_archive.py`。檢查單一應用根目錄、Info.plist、真實啟動入口、執行許可權、ZIP CRC 和安全的符號連結；不允許把外層資料夾當作應用交付。
- 驗收說明已存在於應用內 `Contents/Resources/Release/ACCEPTANCE-2.0.0.md`。本次不修改簽名後的應用內檔案；修訂說明隨原始碼提供。
- 原始碼包及 SHA-256 清單同步更新，未釋出 GitHub Release，OSS 繼續後置。

## 使用

適用 Apple Silicon（M 系列）Mac、macOS 13 或更新版本。

1. 退出正在執行的 Hermes，包括選單欄中的後臺例項。
2. 解壓修訂後的 `Hermes-macOS-arm64-2.0.0.app.zip`。
3. 把得到的 **Hermes.app** 拖到“應用程式”，再從那裡開啟。

若已下載舊包，可先右鍵那個名稱很長的異常應用，選擇“顯示包內容”。如果裡面還有 `Hermes.app`，取出內層應用即可，不必再次下載。該動作不修改使用者配置或伺服器資料。

若隨後出現來源驗證提示，應用仍是原來的 ad-hoc 簽名狀態，未作 Developer ID 公證；這與外層目錄無效是不同的檢查環節。按 macOS 為該具體應用提供的允許開啟流程處理，無需關閉全域性系統保護。

## 已驗證和未驗證

- 原 ZIP 的 SHA-256 與原交付清單一致；不是在本次下載時發生的位元組損壞。
- 原結構被新校驗明確拒絕；修訂結構通過，所有原始應用檔案逐項相等。
- 7 項打包迴歸通過，覆蓋混放說明、錯誤外層應用、缺啟動器、丟執行許可權、啟動器名稱錯誤、越界連結以及正常歸檔。
- 原應用本體 530 項資源封印、47 個 Mach-O 簽名的內碼表與相關特殊槽摘要、85 項 classpath 引用檢查通過。
- 沒有修改 Kotlin 應用邏輯，因此本次沒有重新執行舊版 JVM 功能測試，也沒有把舊測試結果當作本次真機驗證。
- 當前執行環境為 Linux，未執行 Mac 原生 codesign/Gatekeeper、Finder 解壓啟動、麥克風、托盤或真實閘道聯調；修訂 ZIP 不等於經過 Mac 真機驗收的 DMG。
- 使用者所說的其他功能問題還缺少具體操作與錯誤現象，等待反饋後繼續定位。

機器可讀核對結果見 `validation/macos-packaging-r2.json`。
